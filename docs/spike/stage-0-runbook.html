Stage 0, step by step

Seven manual tasks. Work top to bottom — Task 1 gets the spike online, Tasks 4–6 are the measurements, Task 7 closes the stage. Tick each step as you go; progress saves in this browser.

Pair this with the spike page (docs/spike/sensor-spike.html) and record final numbers in docs/spike/STAGE-0.md — that file is the source of truth, this page is the checklist. Exit condition: the target label sits within ±5° of the correct compass direction and does not drift while the phone is still.

1≈ 15 min · once

Put the spike on an HTTPS URL

Camera and motion sensors are blocked unless the page is served over HTTPS from a real origin. file:// and the artifact preview won't work. GitHub Pages is the quickest route since the repo already lives there.

You'll need

  • Push access to github.com/Ashish-119/Treksense
  • The Stage 0 files committed and pushed (docs/spike/…)

Steps

  1. Commit and push the docs/ folder to a branch on the remote (e.g. main or feature/peak-finder).
  2. On GitHub: repo → Settings → Pages (left sidebar).
  3. Under Build and deployment → Source, choose Deploy from a branch.
  4. Set Branch to the one you pushed, folder to / (root), click Save.
  5. Wait ~1–2 min for the green "Your site is live" banner. The URL base is https://ashish-119.github.io/Treksense/.
  6. Open https://ashish-119.github.io/Treksense/docs/spike/sensor-spike.html in a desktop browser. You should see the gate screen with a preflight list.
  7. Confirm the preflight shows Secure context: yes. Send the link to your phones (message it to yourself / AirDrop).
RecordThe live spike URL, so every device uses the same one.
If it goes wrong No Pages option / 404: the repo may be private on a free plan — make it public, or use Vercel instead (import the repo, then https://<project>.vercel.app/docs/spike/sensor-spike.html). Preflight "Secure context: NO": you opened a file:// path or plain http — use the https:// Pages URL.

3≈ 5 min per device

Open the spike and grant permissions

Do this once per device. The order matters on iOS — the motion prompt only appears because you tapped the button.

Steps (repeat per device)

  1. Hold the phone in portrait. Open the spike URL in the default browser (Safari on iOS, Chrome on Android).
  2. Read the preflight list. Expected: all green except "iOS permission gesture" which is amber on iPhone, green (n/a) on Android.
  3. Tap "Start spike & grant permissions".
  4. Grant, in order: Motion & Orientation → Camera → Location (While Using).
  5. You should now see the live camera, a compass tick-strip near the top, and a large heading readout.
  6. Drag the bottom sheet handle up to reveal the readout panel and controls.
If it goes wrong iOS never asked for Motion: reload the page and tap the button again — iOS drops the prompt if anything else grabbed focus first. Still nothing? Settings → Safari → Motion & Orientation Access must be ON. Camera black: check the site's camera permission in the browser's site settings; try "Sensors only (skip camera)" to keep going on the compass tests. Heading readout stuck on "—": Task 4 will tell us why (likely no absolute event — note it and continue).
4≈ 10 min per device

Run the device & sensor audit

The readout panel already probed everything. Walk down it and copy the values. This is blueprint task 0‑1.

Steps (per device, outdoors)

  1. With the sheet open, read each row of the top panel. Copy the values for: source, absolute seen, event rate, gyro rate z, gps accuracy, gps altitude, camera, camera FOV exposed.
  2. Rotate slowly through a full circle. Confirm the heading readout and tick-strip move smoothly and the cardinal letters (N/E/S/W) land in sensible places.
  3. Note the source string exactly — this tells us the heading pipeline for that platform.
  4. Paste the values into the note below (or wait and use the JSON export in Task 7).

5≈ 10 min per device

Drift watch + jitter measurement

Two tests, both with the phone completely still. The first is the pass/fail for the whole stage; the second feeds the smoothing decision (blueprint tasks 0‑3 and the DoD).

5a · 60-second drift watch

  1. In the sheet, set target true bearing to a round number (e.g. 90).
  2. Turn your body until the TARGET label is centred on the reticle and turns green.
  3. Rest the phone on a flat surface (or a tripod) pointing that way. Do not touch it for 60 seconds.
  4. Watch the label. Record: does it stay green / within ±5° the whole minute? Any slow creep?
  5. Repeat facing a different direction (e.g. 0 and 180) — some phones drift only near certain headings.

5b · 30-second jitter test

  1. Lay the phone flat and still, pointing at a fixed mark.
  2. Tap "Start 30 s jitter test". Don't touch the phone until it finishes.
  3. Record the reported σ, peak-to-peak, sample Hz, and the verdict line.
  4. Run it twice more and keep the worst peak-to-peak.

5c · Smoothing feel

  1. While panning back and forth, cycle the smoothing selector None → EMA → Complementary and move the α slider.
  2. Note which setting tracks quickly and settles when you stop. If "Complementary" drifts or runs away, write that down — the gyro sign may be device-specific (that's a Stage 3 finding).
RecordPer device: drift verdict (pass/fail + which headings), jitter σ / peak-to-peak / Hz, and which smoothing felt best.
6≈ 20 min per device

Known-bearing accuracy check

The real test: does the label land on the right direction in the real world, and is the phone's heading true or magnetic north? You need landmarks whose true bearing you can work out.

First — get a landmark's true bearing

Pick something 100 m+ away that you can also pinpoint on a map: a transmission tower, a bridge pier, a lone tree, a distinct summit, or a road that runs dead straight away from you. Then use either method:

Method A — two coordinates
  1. Read your lat/lon from the spike's position row.
  2. Long-press the landmark in Google Maps → copy its lat/lon.
  3. Paste both into any "initial bearing between two coordinates" calculator, or compute
    θ = atan2( sin Δλ·cos φ₂ , cos φ₁·sin φ₂ − sin φ₁·cos φ₂·cos Δλ ), normalised to 0–360°.
  4. That θ is the true bearing (map north = true north).
Method B — the sun (rough, no map needed) At local solar noon the sun sits due south (true 180°) in the Indian Himalaya. Face the sun's horizontal direction at noon and that's your 180° reference; sight the landmark relative to it. Good to ~±3°, fine as a sanity check.

Then — log the checks

  1. Stand still at your measured spot. Aim the centre reticle exactly at the landmark.
  2. Type the landmark's true bearing into "landmark true°" and tap "Log check".
  3. Repeat for 3–5 landmarks in different directions (spread around the compass if you can).
  4. Read the tool's summary: it shows the error assuming raw = true vs raw = magnetic, and which fits better.
  5. Set the spike's "heading is" selector to whichever assumption won (magnetic or already true). Re-aim at a landmark — the TARGET label should now sit within ±5°.
Expected iOS almost always → already true (error vs true < ~3°). Android → usually magnetic, so error-vs-magnetic is small and error-vs-true is off by the local declination (~0.5–2° here — small, but it's the pattern that matters).
7≈ 20 min

Export, declination file, decisions, exit

Pull the data together, grab the one asset, and record the four decisions that unblock Stage 1.

7a · Export each device's results

  1. On each phone, in the spike sheet, tap "Copy JSON" (or "Download JSON").
  2. Paste each blob into the matching ### Device N block in docs/spike/STAGE-0.md → "Results log".
  3. Fill each blob's notes_fill_in fields: driftOver60sPass, cameraLatency (does the video feel real-time?), subjectiveTracking (does the label feel glued to the world?).

7b · Download the magnetic-declination file (blueprint task 0‑5)

  1. Go to ncei.noaa.gov/products/world-magnetic-model.
  2. Download the WMM2025 coefficient file (WMM.COF / WMM2025.COF, public domain, plain text).
  3. Save it as docs/spike/wmm.cof in the repo. Check its size — it should be ~5–6 KB.
  4. Record the size in decision D‑0.2 below. (No code now — the evaluator that reads it is a Stage 3 task.)

7c · Record the decisions

D‑0.1 · Smoothing approach — from Task 5
D‑0.2 · Declination source — from Task 7b
D‑0.3 · Default assumed hFOV per platform — starting values for Stage 3 calibration
D‑0.4 · Target test devices for the rest of the build

7d · Stage 0 exit checklist

  1. Spike deployed to HTTPS and opens on all test devices.
  2. Audit table filled for each device in STAGE‑0.md.
  3. absolute orientation event confirmed present (or its absence noted per device).
  4. 60-second drift watch: pass on the primary iOS and Android devices.
  5. Known-bearing check: label within ±5° of true after choosing the right true/magnetic assumption.
  6. Jitter measured on all devices; D‑0.1 filled.
  7. WMM.COF downloaded, size confirmed; D‑0.2 filled.
  8. D‑0.3 and D‑0.4 filled.
  9. BUILD-LOG.md Stage 0 row set to ✅ with the date.
  10. Send Claude the JSON exports + drift/bearing results to lock D‑0.1 and D‑0.3.
DoneWhen every box above is ticked, Stage 1 — the /api/peaks?bbox= backend — can start.
