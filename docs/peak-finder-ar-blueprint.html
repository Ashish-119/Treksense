TrekSense · Feature Blueprint

Peak Finder — camera, compass, offline

Raise the phone at a skyline and read the mountains back: each summit labelled with its name, elevation and distance, pinned to the real ridge by GPS, compass and tilt. Every peak comes from an on-device store that filled itself the last time there was signal — and keeps re-centring on you, roughly 100 km in every direction, as you travel. No city to type, no connection required in the field.

The redesign

From "type a city" to "point the phone"

v1 was a lookup: choose a start point, call the server, read a list. Useful, but it needs a keyboard, a decision, and a live connection — none of which you have on a ridge at dawn. v2 inverts every one of those.

Dimensionv1 — city lookupv2 — AR peak finder
InputUser types / picks a placeGPS fixes position automatically
OrientationNone — a flat listCompass + tilt place each label on the real peak
OutputSorted list + mini mapLabels over the live camera feed; list is the fallback
ConnectivityRequest per searchZero in the field — served from the on-device store
Data prepOn demand, per queryAutomatic, in the background, whenever there is signal
CoverageWherever the user namesA ~100 km disc that follows the user

The field story

You installed TrekSense at home and opened Peak Finder once — it cached the app and prepared the area around you. On the drive to the trailhead, with patchy 4G, it quietly re-centred the store on each town you passed. At camp, offline, you open Peak Finder: the camera comes up, you pan across the skyline, and Swargarohini I — 6,252 m — 11 km NW tracks the summit as you move the phone. Tap it for the detail card. Nothing loaded from the network.

Scope decisions locked for this draft Full projected-AR overlay · no terrain occlusion for MVP (labels are placed geometrically; nearer ridges may hide a peak) · on-device store holds peak metadata only · flow is automatic first, with a hidden manual-location fallback for denied GPS and bench testing.

How a reading is made

Turning a summit's coordinates into a label on glass

For every peak within range, the projection engine needs two screen coordinates: where it sits left-to-right (from bearing) and up-from-the-horizon (from elevation angle). Both are pure geometry once the sensors give position, heading and pitch.

The pipeline, step by step

// per candidate peak P, observer O, each animation frame 1 d = haversine(O, P) // km; filter d ≤ radius 2 θ_true = initialBearing(O, P) // great-circle, 0…360° from true N 3 head = compassHeading + declination(O.lat, O.lon) // magnetic → true 4 β = normalize180(θ_true − head) 5 x = (0.5 + β / hFOV) × viewport.w // cull if |β| > hFOV/2 + margin 6 Δh = P.elevation − O.elevation 7 α = atan2(Δh − d² / (2·R_eff), d·1000) // R_eff = 7/6·R → curvature + refraction 8 vFOV = hFOV × viewport.h / viewport.w 9 y = (0.5 − (α − pitch) / vFOV) × viewport.h 10 stack labels whose x overlaps; nearest peak on top; draw leader lines

Steps 1–2 and 6–7 are the same haversine and bearing maths v1 already ships, kept local so sorting and panning never touch the network. Steps 3–5 and 8–9 are new and sensor-bound — they are where accuracy is won or lost (see the accuracy budget).

The compass is the weak link Raw phone magnetometers drift ±5–15°. At 40 km that is a 3–10 km sideways error — a label on the wrong summit. Mitigations, all in Stage 3: a figure-eight calibration prompt, a complementary filter to fuse magnetometer with gyroscope, and a one-drag "align this label to that peak" correction the user can apply in the field.

System shape

Two paths to the same overlay

Online, the app prepares; offline, it draws. The projection engine and the overlay renderer never know which mode they are in — they only ever read from the on-device store, which the rolling-window preparer keeps stocked.

The backend proxy

Unchanged in spirit from v1: a Vercel serverless function fronts the OpenStreetMap Overpass API (natural=peak, no key), normalises records, filters non-mountain noise, and edge-caches responses. One change: it takes a bounding box, not a radius, so requests snap to a fixed tile grid (0.5° × 0.5° cells ≈ 55 km) and neighbouring fetches merge without overlap or gaps. The provider layer stays swappable — replace one function, keep the response schema.

The on-device store

IndexedDB, three object stores (see Data model). Peaks are keyed by stable OSM id so refreshes merge rather than duplicate. Tiles carry a status and preparedAt so the preparer knows what to refetch. A prep singleton records the last prepared centre for the staleness badge. The Cache Storage API (via the service worker) holds the app shell and the magnetic-declination asset.

The rolling window

navigator.geolocation.watchPosition feeds a drift check: when the user has moved more than ~15 km from the last prepared centre (or the store is empty) and a connection is available, the preparer computes the tiles covering a 100 km box around the new position, diffs them against the tiles store, fetches what is missing or older than 30 days, upserts, and evicts tiles that have fallen outside a 250 km keep-box along with their orphaned peaks. Storage stays bounded; the user just sees a prepared · 2 h ago chip.

Build sequence

Seven stages, front-loaded on risk

The order is deliberate: prove the sensor loop before building anything on top of it (Stage 0), get real data flowing early (Stages 1–2), then spend the biggest block on the projection engine (Stage 3) where the product either works or doesn't. Durations are for one developer; Stages 1 and 3 can run in parallel once the response schema is frozen.

0≈ half a week

Foundations & sensor spike

Before committing to the architecture, confirm the four sensor APIs behave on the real target devices and build one throwaway screen that proves the core illusion: a label that stays glued to a compass direction as you pan the phone.

Build
  • Pick the magnetic-declination source (World Magnetic Model coefficients, public domain) and confirm asset size < 50 KB
Definition of done

On a real phone outdoors, the spike's label sits on the correct compass direction within ±5° and does not visibly drift while the phone is held still.

1≈ 1 week

Backend + data layer

A Vercel serverless /api/peaks that takes a bounding box, queries Overpass, normalises, filters noise, edge-caches, and falls back to a bundled dataset when the provider is down. Freeze the response schema here — Stage 3 depends on it.

Build
Definition of done

curl a Himalayan bbox returns clean normalised JSON in < 30 s; a repeat call is edge-cached; killing the provider returns the fallback set with degraded:true and HTTP 200.

2≈ 1 week

On-device store + manual preparation

Stand up IndexedDB and the service worker. Preparation is still a manual button at this stage ("Prepare this area") — automation comes in Stage 4. The goal is a hard offline guarantee.

Build
Definition of done

Prepare an area while online, switch the device to airplane mode, hard-reload — the app opens from cache and peaksForBox() returns the area's peaks with no network.

3≈ 1.5 weeks

AR projection engine

The core. A sensor manager that fuses heading, pitch and position into a stable "pose"; a projector that turns each peak into screen coordinates; and an overlay renderer that draws readable, non-overlapping labels over the camera feed.

Build
Definition of done

From a known viewpoint (e.g. above Sankri, facing the Swargarohini–Bandarpoonch wall) each label lands on the correct summit within its own width after calibration; panning is smooth; the drag-to-align correction visibly improves the fit.

4≈ 1 week

Automatic rolling window

Remove the manual "prepare" button. The store now follows the user: a background watcher extends and re-centres the ~100 km disc whenever the user has moved and a connection is available, and trims what falls behind.

Build
Definition of done

Feeding a 300 km mock travel track with intermittent connectivity, the store always covers ~100 km around the mock position wherever a connection was available, and total storage stays bounded.

5≈ 1 week

Fallbacks, polish, accessibility

Every permission and sensor can be denied or absent. Each path must land somewhere useful, and the feature must be operable without the camera and legible to a screen reader.

Accuracy budget

Where the label offset comes from

The label is only as right as the pose. Horizontal error (wrong summit left-to-right) is dominated by the compass; vertical error (label too high or low) by GPS altitude. Everything else is second-order.

Definition of done — the feature

What "working" means

  • A new user opens Peak Finder, grants camera + location, and sees named peaks on the skyline with no further instruction.
  • Names and elevations track the real summits within a label's width from a calibrated viewpoint.
  • With the area prepared, the whole feature works with the network disabled.
  • The ~100 km store re-centres itself as the user travels with signal; storage stays bounded.
  • Every denied permission or missing sensor lands on a usable screen (map mode, manual location, calibration).
  • No provider key or secret is present in client code; repeated views of a prepared area make no provider calls.

Non-goals for the MVP

  • Terrain occlusion / true horizon culling (needs a DEM).
  • Offline basemap or satellite tiles.
  • Peak photographs or 3D panorama rendering in the AR view.
  • Accounts, sharing, saved sightings.
  • Coverage outside the Himalaya (dataset and calibration are region-tuned).
